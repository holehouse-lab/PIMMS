## 1.0.8 (September 2026)

Version 1.0.8 represents a major (although largely-non-breaking or feature-adding) update, primarily in terms of improving test coverage and adding better / updated docstring coverage across the base. We also addressed a number of edge-case bugs and shortcomings; these fixes largely address moves and features added over the last few months, and so touch no previously published work, but a few are long-standing analysis-output errors and are worth calling out:

* The periodic radius of gyration calculation carried a small parallel-axis bias
* Every intra-chain observable of a chain spanning more than half the box was wrong
* `INTSCAL_SQUARED.dat` held the square of a mean rather than the mean of squares
* `DISTANCE_MAP.dat` was only ever half populated.

None of these changes reflect any published work but we're noting this just for completeness! In recent months we did add full seed reproducibility (previously, driven by how random numbers were generated in the Cython/Python codebases this did not happen). In 1.0.8 we have changed how we do the random seeding to (1) remove the risk of repeat patterns in long simulations and (2) ensure full seed-dependent reproducibility. The upshot, however, is that running a simulation with 1.0.7 (or earlier) and 1.0.8 with the same seed will not give the exact same trajectories (although should sample from the same system/distribution).

1.0.8 is also a good deal faster. The per-megamove bookkeeping is compiled, and the energy kernel under every crankshaft, slither and pull substep was restructured so the compiler can unroll it, which makes every long-range and super-long-range energy evaluation 2.5 to 3 times faster; together these roughly halve a default megamove and let `PARALLELIZE` keep more of the kernels' speed-up. Every trajectory is bit-identical. Details are under Performance below.

Below, we outline the major changes, minor changes, and new features/updates as three separate sections.

### Major changes

Major changes change what a run writes, the numbers in it, or the trajectory a given seed produces. If you compare 1.0.8 output against an earlier version, these are the reasons it differs.

#### Output files are created when data are first written to them

For entirely historic reasons PIMMS used to generate empty stubs of every file it might write to. In many cases those files never received any output, so a run left behind a pile of empty files. That behaviour is gone: a file is created at the moment there is something to put in it, so the set of files a run leaves behind is exactly the set of outputs it produced. A disabled analysis leaves no file, and neither does one that is enabled but never fires because its frequency never lands in the production window (easy to hit with the default `EN_FREQ` of 1000 in a short run), nor one that fires with nothing to report (`RES_TO_RES_DIST.dat` with no `ANA_RESIDUE_PAIRS`, `CLUSTER_RADIAL_DENSITY_PROFILE.dat` with no cluster over the bead threshold, `INTSCAL.dat` for a chain type of single beads). A missing file is not an error and is not evidence that an analysis was switched off.

The reason we pre-created files was to guarantee that a run's outputs belong to that run. Start-up now delivers that guarantee by deleting every output the run could write rather than by blanking them, driven from a single manifest in `CONFIG` (`ANALYSIS_OUTPUT_NAMES` and `analysis_output_files()`) that replaces the several ad-hoc stale-removal blocks that had accumulated, and which also covers the per-chain-type `CHAIN_<T>_*` files, the end-of-run files, `QUENCH.dat`, `chain_to_chainid.txt`, the angle summary, the `eq_*` trajectory and, for a resized-equilibration run (which opens `traj.xtc` only at the resize), the production trajectory. `PERFORMANCE.dat` writes its header with its first row.

#### Every intra-chain observable is computed on the chain made whole

Under periodic boundaries the radius of gyration, asphericity, end-to-end distance, internal scaling, distance maps and residue-residue distances were all built from a single image reconstructed by shifting each bead relative to the circular-mean centre of mass, which only works while the chain's extent is below half the box. Beyond that, with no boundary crossing required, a subset of beads was shifted and the chain torn in two: a 25-bead L-shape in a 13-box reported an Rg of 3.82 instead of 5.70, and a real 30-mer run in a 13-box had 17 of 56 `RG.dat` rows wrong. While we'd humbly suggest if you're running a chain in a box this small you have bigger issues to worry about, we recognize this is not great behavior. Similarly, pair distances used the minimum-image convention, which picks the wrong image once a pair is more than half a box apart. Finally, the periodic Rg carried a small one-sided parallel-axis bias because the gyration tensor was referenced to the circular COM rather than the arithmetic mean of the reconstructed coordinates, and `Chain` discarded its hardwall flag, so hardwall observables used periodic geometry.

Every intra-chain observable is now computed on the chain bond-walked into one periodic image, with plain Cartesian geometry, which is exact for any non-percolating chain; hardwall observables use the raw Cartesian coordinates. The old and new conventions agree for every chain shorter than half the box, so results for adequately sized boxes are unchanged. The finite-size warning still fires once per chain whose whole extent exceeds half the box on any axis, which is now more of a concern in terms of inter-image interactions as opposed to the correctness of the analysis. `Chain.get_center_of_mass`, which no output uses, follows the same convention (it had ignored the hardwall flag).

#### Internal scaling and distance maps

`INTSCAL_SQUARED.dat` previously held the square of a mean rather than the mean of squares: the accumulator was fed the per-snapshot pair-averaged distance and squared it, discarding the within-snapshot variance at every sequence gap. `sqrt(INTSCAL_SQUARED)` is now the RMS profile, as it was always documented. The profiles also stopped one gap short, excluding the end-to-end separation, so `INTSCAL.dat` and `INTSCAL_SQUARED.dat` gain a final row, and the scaling-exponent fit can use the most informative point, which the log-spaced point selection had also been skipping. `DISTANCE_MAP.dat` only ever populated its upper triangle and is now the full symmetric matrix. Scripts that hard-code the old row count or read only the upper triangle need a look. An analysis that never sampled (frequency beyond the production length) used to write a plausible-looking profile of exact zeros, or `nan nan` from the fit; it now writes nothing and warns. Worth noting that in Martin, Holehouse, Peran et al. Science 2020, all analysis was done OUTSIDE of the generated trajectories and not within PIMMS, so although we report scaling exponents there, this was done using SOURSOP, so these changes do not affect those conclusions.

#### Cluster analysis

- **Long-range clusters are defined by nonzero interaction energy.** As a quick reminder a "*Chebyshev distance*" of `k` between two lattice sites means that they differ by at most `k` along every axis, so the sites at Chebyshev distance 1 are the 26 (3D) or 8 (2D) nearest neighbours including diagonals, and Chebyshev 2 and 3 are the next two shells out. Short-range contacts act at Chebyshev 1, long-range (LR) interactions at Chebyshev 2, and super-long-range (SLR) interactions at Chebyshev 3. With that in mind, the documented rule is that two chains belong to the same long-range cluster when some pair of their beads either touches or has a nonzero LR or SLR interaction energy. The code did not implement that rule in three ways. First, it joined any two long-range-capable beads within Chebyshev 2 or 3 whether or not their parameter-file entry was actually nonzero, so a parameter file with an all-zero SLR column still joined chains at Chebyshev 3. Second, it left SLR pairs out of the search entirely, so clusters held together only at Chebyshev 3 were split. Third, the search was directional. The pair lists it walked are only ever emitted from long-range-flagged beads, so in a system where some residue types carry long-range interactions and others do not, whether two chains were joined depended on which of them the search happened to start from. The result was not even a partition: the same configuration decomposed into different, overlapping clusters depending on the seed, and in one adversarial run to push the boundaries of this issue we recorded 25 cluster memberships for 20 chains, contaminating every `LR_*` output file. All three of these issues are now fixed. A pair connects only when its LR or SLR table entry is nonzero, SLR pairs are included, and the relation is symmetric, so the clusters form a proper partition. The single-image gather for long-range clusters now walks that same rule when it decides which beads are joined across a periodic face. It used to follow a fixed Chebyshev-3 rule regardless of type or energy, so it wrapped and tore clusters that were not actually in contact with their own periodic image: with a short-range-only parameter file, where the two cluster definitions provably coincide, `LR_CLUSTER_RG.dat` read 2.35 while `CLUSTER_RG.dat` correctly read 2.84 for the identical set of chains.
- **Percolating clusters are marked, not measured.** A cluster connected to its own periodic image has no radius of gyration, convex hull or radial profile; the numbers written for one are an artefact of the search order (re-rooting the gather at each bead spanned 2.97 to 3.87 for a single fixed configuration). Such clusters are now detected at the gather (by an actual pair of beads touching through a face, not merely by extent), their shape and hull columns are written as `nan` or `-1`, their radial row is omitted, and every occurrence goes to the run's log.
- **Cluster shapes.** `extract_cluster_polymeric_properties` received single-image positions but re-applied the periodic correction in a bounding box barely larger than the cluster, inflating Rg by up to 15% for elongated clusters; it now computes plain gyration properties. The single-image gather's shift to non-negative coordinates was not a whole number of box periods, so the "single image" of a cluster straddling a low face sat in an arbitrary frame and lemonade's cluster centre of mass landed up to a cluster radius from the truth; the shift is now a whole number of periods.
- **Radial density profiles.** Under periodic boundaries beads were binned by single-image distance while normalised by the full periodic shell, so a bead whose image occupied a shell site was dropped (the trigger is asymmetry about the centre, not size); the periodic branch now bins on the minimum image. Under a hardwall, shells running through a wall were normalised by the full periodic shell size, so a film on a wall read as 65% full when it was completely full, and shells beyond the farthest in-box site were reported as density 0 rather than "no data"; hardwall shells are now normalised by the sites inside the box and empty shells are `nan`. The profile centre is the plain rounded mean of the single-image positions (the periodic COM wrapped to the far side of the box for edge clusters and zeroed the whole profile). Profiles filtered by the bead threshold were renumbered from `C1`, silently attributing a later cluster's profile to an earlier one; they now carry their original one-based cluster index.
- `CHAIN_<type>_CLUSTERS.dat` rows now lead with the step number, like every other per-step file.
- **The percolation test is exact, and linear in memory.** A cluster is flagged as percolating when any of its links closes a loop around the box, however many box lengths the loop takes. The old test compared extents and then built a pairwise matrix over the beads near the box faces: it missed clusters that only close after winding a short axis twice (written with an ordinary Rg, hull and radial profile), and its memory grew with the square of the cluster size (16 GB for a 10^5-bead network; 848 MB against 42 MB now for a 7,000-bead melt). Each cluster is also tested once per analysis step rather than twice.
- The radial-profile centre rounds halves up rather than to the nearest even site, so the profile is unchanged when the whole cluster is translated by one site. Rows of `CLUSTER_RADIAL_DENSITY_PROFILE.dat` and `LR_CLUSTER_RADIAL_DENSITY_PROFILE.dat` can differ from earlier output when a cluster's mean position falls exactly on a half-integer.

#### Sampling and detailed balance

- **`PARALLELIZE` biased chain conformations for `MOVE_SLITHER` and `MOVE_PULL`.** This one is worth understanding properly, so here is the background first.

  *How the parallel megamoves work.* With `PARALLELIZE : True`, a slither or pull megamove splits the box into a grid of blocks and hands each block to its own thread. To keep the threads from stepping on each other, every block has a frozen border, or "halo", a few sites wide; nothing in the halo moves during that sweep, and a chain is only allowed to move if it sits entirely inside one block's interior, the part that is not halo. The one thing a parallel kernel can never do is push a chain out of its interior, because that would take it into a halo where another thread might be working. So a chain that is small enough to fit inside an interior gets moved by the parallel kernel, and a chain that is too spread out to fit anywhere just sits still for that sweep. The block grid is shifted by a random offset every sweep, so which chains fit changes from sweep to sweep and over a long run everything gets its turn. The serial kernel has no blocks and no halos, and moves every chain freely.

  *What used to happen.* Before running each megamove, PIMMS looked at the current positions of every chain and asked whether all of them fit inside a block interior right now. If they all did, it ran the parallel kernel. If even one did not, it fell back to the serial kernel for that megamove. That sounds reasonable, and every energy check passes, but it is a subtle mistake. Take a chain that is right on the edge of fitting. When it is compact, the parallel kernel is chosen, and the parallel kernel can only ever move it in ways that keep it compact, because it cannot extend it out of the interior. When it is expanded, the serial kernel is chosen, and the serial kernel is perfectly happy to let it curl back up. So there is a one-way street: stretched chains can become compact, but compact chains are prevented from becoming stretched. Each kernel on its own samples the right distribution, but switching between them based on the current configuration does not, and the run drifts towards compact chains. In a test box of 8-bead chains at infinite temperature, where every conformation should be equally likely, the probability of seeing an extended chain was cut in half and the mean squared radius of gyration came out about 3% low, always in the same direction. Nothing flagged it. The energy is tracked perfectly, the move logs look normal, and the start-up report cheerfully announces the parallel kernel.

  *What happens now.* The decision of which kernel moves which chain is made once, at the start of the run, from chain length alone: a chain that is short enough that it could always fit inside an interior goes to the parallel kernel, and every longer chain goes to the serial kernel, and both kernels run in every megamove. Because the split depends only on how long the chains are, never on where they happen to be, the one-way street is gone. Long chains keep reptating through the serial kernel, so nothing is ever stuck, and short chains keep the parallel speed-up. The start-up report now tells you how many chains went each way. Two details make this exact. The random block shift is drawn over the whole box rather than one block length: when a box side does not divide evenly into blocks, the shorter draw never placed some start positions inside an interior, so a chain as long as the interior sitting there was never moved by the parallel kernel it had been assigned to (a straight 6-mer at x = 2 in a 25-site box). And the two passes run in an order drawn by a coin flip each megamove: a fixed order preserves the Boltzmann distribution but is not reversible, which a system-wide TSMMC excursion requires of its sub-moves.

  *Who was affected.* You need a box big enough to split into blocks in the first place (at least 24 sites on a side with short-range interactions, 40 with long-range ones) and chains whose extent hovers around the interior size, which for typical boxes is roughly 7 to 12 beads in a 24 to 48 site box. Collapsed globules, very short chains, small boxes and runs without slither or pull were never affected. If you have a `PARALLELIZE` run with coil-like chains in that range and cared about their dimensions, that run is worth repeating.
- **`PARALLELIZE` samples the same equilibrium as the serial kernels but relaxes more slowly per step.** In testing the parallelize keyword, we noticed that running the same system with `PARALLELIZE` on and off returned "different final energies". This was not a bug, – just differences in the sampling strategies – but reveal three small issues  with the crankshaft's parallel kernel.

  *Why the energies differ.* The parallel crankshaft uses the same block-and-halo scheme described above: only beads inside a block's interior can move in a given sweep, and a proposal that would land a bead in a frozen halo is rejected. Both of those are perfectly legitimate, and the parallel kernel provably samples exactly the same equilibrium distribution as the serial one. What it does not do is get there as fast. In every sweep a chunk of the box is off limits, so the parallel chain makes fewer useful moves per step and takes longer to relax. If your system is still collapsing when you look at it, the parallel run will look less collapsed than the serial run at the same step count, because it is behind, not because it is heading somewhere different. From the same starting configuration, a collapsing 44-site long-range box reached an energy of −32480 after 150 serial sweeps and only −27747 after 150 parallel sweeps, with identical numbers of attempted moves. Let both run to equilibrium, and they agree. This means step count for parallel vs. serial kernels do not provide equivalent degrees of sampling, potentially undermining the advantage that parallelization provides.

  *Three updates:*

  First, the halo was wider than it needed to be. The frozen border was five sites wide with long-range interactions and three without, which was the width you would need if a move could land in the halo. Since moves are never allowed to land in the halo, a much thinner border is enough to keep the threads apart: two sites with long-range interactions and one without. On that 44-site box this raises the fraction of the box that can move in each sweep from 16% to about 55%, which dramatically reduced the slow-relaxation penalty.

  Second, the kernel was making fewer moves than it said it was. `CRANKSHAFT_SUBSTEPS` is divided between the blocks, and that division was rounded down for every block, so up to one attempt per block was lost in every sweep, and if you asked for fewer substeps than there were blocks you got none at all. The move logs recorded the full number anyway. The remainder is now shared out so that exactly the requested number of attempts is made. Separately, a sweep whose random shift leaves nothing movable makes no attempts in any of the parallel kernels, and was logged as the full budget rejected, understating `ACCEPTANCE.dat` (5.7% against 89.6% serial for two free 5-mers in a 48-cube); the kernels now report the attempts they make.

  Third, the per-block random number streams were not independent. Each block's stream was seeded from `block + seed`, so block 3 in one sweep drew exactly the same numbers as block 2 in the next sweep, and adjacent sweeps replayed each other almost entirely. Each block now gets a properly scrambled seed, and this is checked by a test that looks for any repeated stream; this also prompt the change in how we do random number generation (described above).

  None of this changed what `PARALLELIZE` converges to, and results are still identical for any number of threads.
- **VMMC violated detailed balance, in three separate ways.** VMMC is the experimental collective move (`MOVE_VMMC`, off by default) for getting stuck condensed systems moving, implemented based on beautiful work from Whitelam & Geissler (J. Chem Phys. 2007). All three issues are fixed, although we keep VMMC as an `experimental` move for now.

  *How VMMC works.* A single chain is picked and given a trial shove. Rather than moving it alone, the move then asks each of its neighbours in turn whether it would rather come along: for every neighboring chain it computes how much the interaction energy between the two would change if the shoved chain moved and the neighbour stayed put, and if that would break a favourable contact, the neighbour is recruited with a probability set by that energy change. Recruited chains then recruit their own neighbours, and so on, until the cluster stops growing. The whole cluster is then translated rigidly. Because the cluster was built by a random process that depends on the energies, the acceptance rule is not just a simple Metropolis acceptance. Every link the recruitment tested – whether it succeeded or failed – has to contribute a correction factor comparing how likely that outcome was going forward with how likely the mirror-image outcome would be coming back. Get any of those factors wrong and the move stops sampling the Boltzmann distribution.

  *Problem one: failed links to chains left behind.* When a link is tested and fails, the neighbour stays where it is while the cluster moves away. The reverse of that move, coming back, tests the same link from the other side, and the probability that it fails again depends on the energy between the neighbour and the cluster *after* the cluster has moved. The code was instead using the energy that applies to a neighbour that moved *with* the cluster, which is a different quantity. The bias was large and always favoured contact: for two single-bead chains, where the exact answer can be enumerated, the move put them in contact 86% of the time when the correct answer was 43%.

  *Problem two: frustrated links.* Sometimes a link from chain A to chain B is tested and fails, but B ends up in the cluster anyway because chain C recruited it. That tested-and-failed link still has to contribute its factor to the acceptance ratio, because in the reverse move it would be tested again. The code was leaving those links out entirely. This one is easy to miss because it needs at least three chains to happen at all, and the earlier two-chain checks could not see it. With three single-bead chains enumerated exactly, the forward and reverse rates between two states of identical energy differed by up to 36%. The fix gives frustrated links the reverse probability appropriate to a partner that is inside the final cluster, tests links in a fixed order so that every forward recruitment has a well-defined mirror image, and builds the whole acceptance ratio in one place that is tested on its own.

  *Problem three: hard walls.* Under a hardwall, the recruitment step correctly treated a chain that would be shoved outside the box as simply not there. But the step that actually commits the move wrapped that same chain around to the other side of the box, periodic-style. So the move accepted or rejected based on one configuration and then committed a different one. Hardwall VMMC now rejects any proposal that would take a bead outside the box, before anything is moved, which is the same rule the other collective moves use.

  **NB**: - I still don't consider VMMC safe for production ;-), so right now I'd encourage folks to PLAY with it if they have systems where it makes sense, but probably not use it for real science.
- **Rigid rotations were not invertible.** `chain_rotate` and `cluster_rotate` rotated about the rounded circular-mean centre of mass, which is generally a different lattice point after the rotation, so about a third of accepted chain rotations and cluster rotations could not be reversed. Moreover, `cluster_rotate` never rotated a boundary-straddling cluster as a rigid body. Both now rotate displacement vectors about the bead nearest the centroid, selected by exact integer arithmetic (a float argmin broke ties by rounding noise that is not rotation-invariant), and re-anchor on that bead's original position; `cluster_rotate` single-images the cluster first under periodic boundaries and uses the raw Cartesian coordinates under a hardwall, where it used to refuse any axis-spanning cluster and, in a non-cubic box, refuse one direction only. Rotating a cluster that winds around the periodic box is not a rigid motion and is rejected. Rotations that map the body exactly onto itself (a straight axis-aligned chain about its own axis, an isolated monomer about itself) were counted as accepted moves, inflating cluster-rotate acceptance in a monomer-rich system by a factor of two and a half; they are now rejected, which changes nothing about what is sampled.
- **`cluster_translate` proposals were directional.** Chains were deleted from the grid one at a time, each re-placed at its translated position, so a bead landing on a cluster-mate's not-yet-vacated site was a hard-core clash whose occurrence depended on the direction of the shift (0 versus 2151 successes in 200,000 trials between two states of identical energy). Now, the whole cluster is removed before anything is placed. It's worth noting this is what we had for a long time, and the sequential range was added to improve efficiency, and fails specifically where cluster-to-box ratios are small, which is also when cluster translation is least useful. It makes sense to fix but unclear if the old behavior actually had any truly meaningful issues... Under a hardwall a box-spanning cluster could be "translated" by permuting its chains through the wall with the wrong energy; raw out-of-box coordinates are now rejected. `rigid_cluster_move` also counted every intra-cluster long-range pair once from each end.
- **`chain_pivot` was off by one.** The N-terminal arm anchored on the bead before the pivot, so pivot point 1 was a guaranteed null move that was still energy-evaluated and logged as accepted; 3-mers never moved at all and one terminus of a 4-mer was unreachable. Both arms anchor on the pivot bead.
- **Monomers walked through hard walls** in every crankshaft and slither kernel, because a single-bead move was wrapped and never straddle-checked. All kernel proposal sites now reject it.
- **Temperature-excursion moves.** The system-wide TSMMC protocol was not palindromic (it ran the first sub-moves at the target temperature and never visited the last schedule temperature), which the tempered-transitions acceptance requires; the executed schedule is now exactly `[s0 xM, ..., s_(L-1) xM]`. The linear schedule overshot `TSMMC_JUMP_TEMP` for about 6% of parameter combinations through `np.arange` with a float endpoint. Inside a system-wide excursion a nested TSMMC draw was remapped to a crankshaft megamove even with `MOVE_CRANKSHAFT : 0`; it is now redrawn from the non-TSMMC moves with their fractions renormalised.
- **Move selection no longer depends on the chain that happened to be drawn.** A rotate, pivot or head-pivot draw on a single-bead chain, and a slither or pull draw when the outer-loop seed was a monomer, were silently remapped to a whole-system crankshaft megamove regardless of `MOVE_CRANKSHAFT`, so the executed move mix in any system with monomers was composition dependent and contradicted the keyfile (six monomers with rotate 0.5 / translate 0.5 logged 7500 crankshaft attempts in 30 steps). Such draws are now rejected as null moves, and the start-up summary says what fraction of steps that costs. The last move-selection interval is snapped to exactly 1.0 when float accumulation leaves it a hair short, which used to crash a run about once per 1e8 steps.
- **Move sets that cannot change a conformation now warn.** A set built only from rigid moves leaves every chain's shape invariant, so `RG.dat` and `END_TO_END_DIST.dat` repeat the same rows and the scaling exponent is fitted to constant data; pull with any rigid move fixes every end-to-end distance, head-pivot alone never moves an interior bead, chain-pivot alone never moves the middle beads. This is not a detailed-balance defect: the chain is reducible and samples the Boltzmann distribution restricted to the conformations it started in. PIMMS warns at start-up and names the affected files. It warns rather than refuses, since a rigid-only move set is the legitimate way to study rigid-body assembly of fixed-conformation chains.
- **The serial kernels accepted any uphill move with probability at least 2^-31.** The crankshaft, slither and pull kernels drew a 31-bit acceptance number, and a draw of exactly 0 passed for any positive Boltzmann factor: 13% too often at `beta dE = 20`, 33 times too often at 25, and flat at 4.7e-10 from about 21.5 up to the float32 underflow near 103, so a penalty meant as "forbidden" was not. The test now has a second stage, reached only when the draw lands in the one bin that holds the factor, which makes the accepted probability the factor itself. Existing serial trajectories are unchanged unless a draw lands in that bin (2^-31 per uphill test). The parallel kernels and the Python moves never had the floor.
- **`PARALLELIZE` crankshaft: the block shift is drawn over the whole box.** It was drawn over one block length, so on an axis that does not divide evenly into blocks a bead's sweep rate depended on its absolute coordinate (movable in 50% to 75% of sweeps along a 26-site axis). Equilibrium was never affected; `PARALLELIZE` crankshaft trajectories change.
- **Cluster-only move sets.** `MOVE_CLUSTER_TRANSLATE` and `MOVE_CLUSTER_ROTATE` reject merges and never split a cluster, so a move set made only of them can never form or break a contact. Such a run now warns that the contact graph is frozen, and is refused when no mobile chain can ever move (every mobile chain shares a cluster with a frozen chain, one cluster holds every chain, or isolated beads under rotation alone). The same holds when other moves are enabled but too short to act on any mobile chain; the refusal depends on the starting placement and says so. The rigid-only warning now covers dimers, whose bond (axial, face-diagonal or body-diagonal) rigid moves never change.

#### Simulation loop and output cadence

- `ENERGY.dat`, trajectory frames, and every analysis were written before each move while labeled with that move's step, so every row was one move behind and the final state was absent. Scheduled output now runs after the completed move, including the self-contained megamoves; a row labeled step `N` describes the state after step `N`.
- Step `EQUILIBRATION` is the last equilibration step everywhere: analysis and restart snapshots start at the first multiple of the frequency strictly greater than it (they used to analyse that one step), the `PERFORMANCE.dat` E/P column agrees, and with `RESIZED_EQUILIBRATION` the box swap happens after that step's move rather than before, so the last equilibration frame stays in `eq_traj.xtc`.
- A system-wide TSMMC excursion selected at step `i` no longer consumes two step numbers and repeats that step's quench or resize update, and one selected on the final step is allowed to finish rather than being serialised half done. Fully frozen no-op steps still run scheduled output.
- `SAVE_AT_END` appended a mislabelled final frame when no step qualified for one, and in a resized run wrote production coordinates into `eq_traj.xtc`; both save frame 0 only, as the incremental writer does.
- `AUTOCENTER` wrote a boundary-straddling chain entirely outside the box (the centre was taken from the periodic COM of already-unwrapped positions), put every coordinate half a site off the lattice on an odd box axis, and did not apply to `START.pdb` or frame 0.
- Quench runs: fractional ramps were mis-counted on binary floats (`1.0 -> 0.7` by `0.1` was four rungs, `0.3 -> 0.2` by `0.1` was refused as an overshoot), the accumulated stepsize error fired the "target reached" test one rung late, cooling below T = 1 was refused, `QUENCH_AS_EQUILIBRATION` sized the window from `int(dT)`, and a heating ramp that reached `TSMMC_JUMP_TEMP` crashed or silently inverted the excursion. All fixed; rung counting uses a relative `1e-9` tolerance, the quench snaps to its target, and the jump temperature is checked against the hottest temperature the ramp visits. `QUENCH.dat` carries six significant figures (a `0.025` stepsize used to record `0.97/0.98, 0.93, ...`) and its energy is the post-move energy at that temperature.
- `TOTAL_MOVES.dat` no longer counts a system-wide TSMMC excursion as an attempt on top of its substeps.
- `SIGTERM` and `Ctrl-C` are clean stops (exit status 143 and 130, no traceback): either leaves one line on screen and in `log.txt` giving the step reached and the step of the checkpoint on disk, closes the trajectory, and under `SAVE_AT_END` writes the buffered frames. A further signal arriving during the clean-up is ignored.
- A start that fails writes `START FAILED - NO SIMULATION WAS RUN` to `log.txt`, and `keyfile_used.kf` is written only once the simulation is built and its trajectory open, so a failed start no longer leaves files describing a run that never happened beside an older run's data.
- An input file that is also one of the run's output files (a parameter file called `log.txt`, say) is refused before anything is written. `pimms_running.pid` holds one line per run using a directory, and a run started there while another is still going warns.
- A stale output file that cannot be deleted at start-up is reported rather than silently kept and appended to; outputs created afresh replace a symbolic link rather than writing through it; scratch files left by a run killed inside a write are removed at the next start-up.

#### Trajectory and PDB output

Atom serials overflowed the five-column field at 100,000 beads and crashed the run; they now wrap modulo 100,000 (lemonade never reads them, and a 101,000-bead run round-trips), and a `CONECT` record is written only when both of its serials are unique in the file (bonds between reused low serials attached atoms at the far end of the file: 2,982 molecules for 1,010 chains). The `TER` record carried a residue number one past the terminal residue, which crashed for chains of exactly 9999 beads. Chain types were labelled `A-Z` with every further type falling back to `Z`, so lemonade merged types 26 and up without a keyfile; they are now `A-Z`, `a-z`, `0-9`, byte-identical up to 26 types. ATOM coordinates and the MODEL serial are column-exact against the wwPDB spec (`1.5` was centre-padded, which strict readers misparse). Streamed XTC frames carry sequential time and step metadata rather than all being stamped zero.

- The streamed `traj.xtc` is flushed after every frame, so a killed run keeps every completed frame (a kill or a concurrent read inside a frame write can leave a torn final frame, which `lemonade.load` drops). It used to sit in a buffer: a `SIGKILL` left an unreadable file and lost frames from before the last checkpoint, which a continuation never writes again.
- `SAVE_AT_END` writes the same bytes as the streamed trajectory. The unit cell comes from `DIMENSIONS` x `LATTICE_TO_ANGSTROMS` (it was the rounded `CRYST1` record read back from `START.pdb`, a `TypeError` at the first frame below about 1 Å per site, and carried 1e-6 nm off-diagonal terms above about 23 nm); nothing is joined in memory at the end; and a write that fails part-way leaves whole frames only and can be retried.
- PDB files are written to a temporary name and moved into place. A box of 10,000 Å or more along an axis does not fit the PDB coordinate columns and is refused when the keyfile is read; it used to crash after equilibration and leave a truncated `START.pdb`.
- `AUTOCENTER` under `HARDWALL` no longer writes beads outside the box (the chain is centred as far as the walls allow), and with more than one chain it warns that it has no effect.

#### lemonade

- **`load()` resolves the run's effective configuration, not the literal keyfile.** `HARDWALL` and `DIMENSIONS` are taken from the restart file when `RESTART_OVERRIDE_HARDWALL` or `RESTART_OVERRIDE_DIMENSIONS` says so (a wall-confined dilute solution analysed as periodic clustered through the walls and was reported as a percolating condensate, wrong in every frame, with no warning), the `eq_traj.xtc` of a `RESIZED_EQUILIBRATION` run loads under the forced hard walls it was simulated with, a restart keyfile's `CHAIN` lines are not applied (PIMMS discards them and merges `EXTRA_CHAIN` by sequence), the temperature of a `QUENCH_RUN` keyfile is `QUENCH_END`, and the loader refuses to guess when a needed restart file cannot be found. Keyfile chain types are applied only when they reproduce the PDB's own chain-type partition: with a restart run's `keyfile_used.kf` (types grouped, trajectory in chain-ID order) twin-sequence types were silently mislabelled, and an `EXTRA_CHAIN` merge raised a false mismatch warning.
- **Hardwall trajectories were analyzed as periodic.** `TrajectoryStore` stored the flag and never consulted it, so chains against opposite walls were merged into one cluster and the gather dragged one across the wall. The connected-component search, single-image gather, radial profiles (Cartesian, wall-truncated shells, `nan` beyond the box) and slab analyses (no periodic roll, wall faces excluded from the capillary spectrum, a wall-wetting film fit with a single-interface model, a free slab aligned by its dense centroid, the slab centre a fitted parameter) all honour the walls now; the two-face surface tension of a film on a wall used to come out exactly double. The hardwall slab profile no longer averages wall-touching and free-slab frames together (the minority kind is left out with a warning; mixing them gave `rho_d` 0.84 for a slab of density 1.0) or pads vacated planes with the median dilute count (the dilute density read about 25% low); each plane is averaged over the frames that cover it.
- **`phase_separation.analyze` reported homogeneous solutions as phase separated.** At moderate volume fraction the contact clustering percolates, the rounded centre of mass lands on a bead, and the one-site innermost shell reads 0.6 to 0.9 against a flat background; fitted with the same weight as thousand-site shells it became `rho_dense = 1.0, success = True` for uniformly random occupancy. The radial fit ignores shells with too few sites (20 in 3D, 8 in 2D), rejects fitted radii below two sites, and `PhaseSeparationResult` gained `percolation_fraction` and `spanning_fraction`, with `is_phase_separated` requiring the former below 0.5. A slab sitting away from the walls was routed to the wetting fit and reported as not phase separated; an inverted two-interface fit is rejected rather than reported with the densities swapped; fallback densities no longer include the one-site shell that the fit discards.
- **Surface tension.** The capillary-wave fit uses the exact lattice dispersion `2 - 2cos(q)` rather than continuum `q^2` (2% low on a 20x20 cross-section, 12% on 8x8), independent modes are selected by canonical `+q/-q` pairs rather than by equal power, the droplet estimator sizes its angular grid from the median largest cluster rather than a fixed 8x16 grid or from the first frame with any cluster (which returned `nan` without a word after an uncondensed leading frame), and a fluctuation-free slab returns `gamma = +inf` explicitly. The slab estimator skips, with a warning, frames whose largest cluster spans the slab normal or misses an in-plane axis (it returned a finite gamma for a one-phase network). Wetting-film thickness is measured from the wall face rather than the centre of the first lattice plane, so a film of `t` planes reports `t` rather than `t - 0.5`, which was 17% at three planes and one-signed.
- **`droplet_shape` and the radial density profile leave out frames whose largest cluster spans the box.** A cluster connected to its own periodic image has no single image: the gather hands back one search-order-dependent window of it, and the radius of gyration, asphericity, hull and centre of mass of that window describe the search, not the cluster. Both routines averaged such frames in with the droplet frames, and `analyze` reported the result without a marker (it only marks the *fit* unusable, and only when most frames span). The usual case is frame 0 of a run that saved its equilibration, a random placement that percolates as a contact network: on the shipped condensed fixture it is 1 frame of 31, and in a ten-frame example an asphericity of 15 for that frame moved the mean from 0.0 to 1.5. Spanning frames are now skipped, as `droplet_surface_tension` already did, and a warning names how many; `spanning_fraction` reports the same count. Under a hardwall the same frames are left out for a different reason, which the warnings state: a cluster touching both walls has an exact centre of mass and a well-defined profile, but it is a wall-bounded film or network, not a droplet. When every frame spans the profile about the arbitrary centre is still returned, with its own warning, because its percentiles remain `analyze`'s fallback estimate of the two densities on a network. The spanning detector itself now delegates to PIMMS's percolation test (`cluster_utils.percolating_axes`): reaching the box length on an axis is necessary for winding but not sufficient, and lemonade's extent-only copy counted a corner-to-corner contact staircase as spanning while the gather correctly did not, so `spanning_fraction`, `percolation_fraction` and the surface-tension frame skip were all slightly over-counted on such configurations. The per-axis answer is cached on the lemonade `Cluster` as `Cluster.spanning_axes()`, computed once per gather in place of the gather's own test rather than twice, and `cluster_percolates` keeps its first-axis early exit (`percolating_axes(first_only=True)`).
- A 2D `DIMENSIONS` on a 3D trajectory silently discarded every z coordinate (nine clusters became three); the box cross-check compares dimensionality and applies to an explicit `dimensions=` too. A 3D configuration lying in a plane is no longer flattened to 2D; the box record decides. The lattice round-off residual warns above 0.05 whether or not `verbose` is set (a wrong `LATTICE_TO_ANGSTROMS` used to break every bond silently), and a keyfile `DIMENSIONS` that disagrees with the trajectory's own box record warns loudly. Lower-case keyfile chains were silently dropped and are now honoured under `CASE_INSENSITIVE_CHAINS`. `analyze(geometry='slab')` no longer reports shape statistics, since the convex hull of a box-spanning slab is meaningless. `Cluster.radial_density_profile()` entry `k` is the shell at Chebyshev distance `k + 1`, matching the `.dat` file; the lemonade docs had said `k`.
- **`phase_separation.analyze` no longer reports a one-phase solution as phase separated in slab geometry.** Centring every frame on its densest region lines fluctuations up into a hump, and under hard walls the two-interface fit took the wall depletion layer for the dilute phase. A slab must now hold at least three standard deviations more chains than a uniform solution would put in the same planes, and its dilute plateau must be wider than a chain. On 202 one-phase runs 96 were reported phase separated before and 0 now; of 75 clear two-phase runs 74 are accepted, as before. Not settled, and named in the docs: runs near the critical temperature, fragmented condensates in narrow hardwall boxes, hardwall condensates that fill the box, and systems of only a few chains (a slab of a dozen chains filling half the box, or a single collapsed chain, is now reported as not phase separated).
- In droplet geometry the density gap must be resolved in single frames (5 of 54 athermal runs were reported as a droplet, 0 now), and `fit_radial_profile` rejects a profile that ends before its dilute plateau. New: `PhaseSeparationResult.chain_excess_sigma` and `slab_axis`, `analyze(axis=)`, `slab_normal`, and `min_dilute_planes=` / `frame_scatter=` on `fit_slab_profile`.
- A one-phase `HARDWALL` trajectory's slab profile is the plain per-plane mean (it was translated by a noise centroid, or split). The slab normal is the axis the condensate does not span rather than always the longest; a negative `axis` is normalised and range-checked; one-plane films are rejected with a slab-specific reason and a condensate wetting both walls is fitted; the radial-profile centre rounds halves up, as in the engine.
- `slab_surface_tension` projects on cosine modes under `HARDWALL` (the periodic transform read 0.55 of the true value on synthetic capillary spectra) and warns that the hardwall estimate is not reliable on real hardwall slabs.
- `load()` opens the trajectory of a running or killed run: a torn last frame is dropped with a warning giving the number of complete frames recovered. It also checks that the bonds of the first frame are single lattice steps, so a spacing that is a whole multiple of the assumed one (which leaves no round-off residual) now warns and names the probable spacing.
- `load()`: a single-chain hardwall trajectory with beads outside the box (what `AUTOCENTER` wrote before 1.0.8) is translated back inside rather than wrapped through the wall; with 62 or more chain types a keyfile may split only the shared last PDB identifier, and restarts recover merged types from the restart file or `keyfile_used.kf`; non-ASCII trajectory paths work; a bool `spacing` is refused; the box is taken from the PDB's `CRYST1` record when the trajectory carries none, and mdtraj's warning that it discarded that record is no longer passed on.
- Equal-size clusters are ordered by lowest chain index (it was search order). In a frame with a tie for the largest cluster, `radial_density_profile`, `droplet_shape`, `spanning_fraction` and `largest_cluster_size(by="chains")` can differ from earlier output.

#### Removed, renamed and reseeded

- The obsolete `initialized_systems.py` neurofilament demo and its private `Chain(fixed=True)` mechanism are removed; `FREEZE_FILE` is the single way to hold chains immobile, honoured consistently by serial, collective and parallel moves.
- Dead compiled modules `get_randmax`, `lattice_tools` and `random_number`, the `cython_backup/` directory (three stale kernel snapshots that shipped in the wheel), `lattice_utils.append_to_xtc_file` (rewrote a scratch PDB and re-saved the whole XTC every frame) and its uncalled sibling `append_to_xtc_file_non_redundant`, `mega_crank.randint_tester`, the three uncalled `write_status` methods, the `OUTNAME_INTER_INTRA` and `OUTNAME_MIXING` constants and the pre-scipy-0.17 hull fallback are gone. `AcceptanceCalculator.move_selector()` no longer takes a chain length, `KeyFileParser.parse` drops its unread `verbose` flag, and the fast energy kernels drop the occupancy grid they never read.
- `CRANKSHAFT_MODE` is accepted with a warning and ignored rather than refused, so old keyfiles keep working.
- PIMMS is a coarse-grained model and its particles are beads, but lemonade and a handful of docstrings, comments and pages called them atoms, a habit inherited from the PDB and XTC vocabulary. lemonade's `n_atoms` is now `n_beads` on the trajectory, frame, store and topology objects (the old name remains as a deprecated alias that warns), `Topology.atom_chainid` is `bead_chainid`, the lemonade kernel's parameters and every array-shape docstring say beads, and the pages say bead order where they said atom order. The word survives only where it names something that really is one: a PDB `ATOM` record, serial or atom-name column, and mdtraj's own attributes.
- numpy's global generator was seeded with `SEED` reduced modulo `2^31 - 1`, the reduction the reference kernel's C `int` seed needs, so seeds `s` and `s + 2^31 - 1` shared their bead-selector and shuffle streams (their Python and kernel streams differed, so no two runs were identical and sampling was unaffected). It is now seeded modulo `2^32`; seeds below `2^31 - 1`, which is every seed in the regression fixtures, are unchanged.
- **The compiled kernels are now seeded with the full random draw.** Every megamove hands the compiled kernel a fresh seed, drawn from Python's random number generator, and the kernel's own generator then produces that megamove's entire sequence of proposals and accept/reject decisions from it. Two megamoves given the same seed therefore make exactly the same sequence of random choices. The seed used to be reduced modulo `2^31 - 1` before being handed down, a leftover from when the kernels used the C library's `rand()`, which meant there were only about two billion possible seeds and so only about two billion possible sequences. In a long run that is not enough: by the birthday bound, 300,000 megamoves produced 14 pairs that had been given the same seed, and a run of ten million megamoves would produce around 23,000 such pairs. This did not bias anything, because the seed is drawn without reference to the configuration and each megamove is still exactly the intended Metropolis kernel, but two megamoves that share a seed are not independent samples, so it quietly inflated the variance of every time average. The seed is now passed down at its full 63 bits, which makes a repeat effectively impossible. Separately, the modulus itself (`C_RAND_MAX`) is now the fixed constant `2^31 - 1` rather than the platform's `RAND_MAX`, which on Windows is 32767 and had collapsed the seed space there to fifteen bits. **Because the kernels now see different seeds, every random stream changes**: a 1.0.8 run does not reproduce a 1.0.7 trajectory for the same `SEED`. Reproducibility within 1.0.8 is unaffected.
- All fifteen regression baselines were regenerated from this tree. The earlier ones were recorded against whatever `PIMMS` was on `PATH`, in practice a pip-installed 1.0.1, so they were never a like-for-like reference.

### Minor changes

Edge-case fixes, validation and hardening. None of these changes the numbers a correctly configured run produces.

#### Keyfile, parameter and freeze files

- `RESTART_OVERRIDE_DIMENSIONS` replaced the box after the keyfile checks had run, so a too-small restart box or a non-cubic box with `MOVE_CLUSTER_ROTATE` under periodic boundaries went through; `RESTART_OVERRIDE_HARDWALL` likewise bypassed the cluster-rotate box rule and the periodic-restart-with-`RESIZED_EQUILIBRATION` check. Every restart rule now runs once on the final `HARDWALL` and `DIMENSIONS`. The resized-equilibration phase itself always runs under a hardwall, so only the production box needs to be cubic for cluster rotation.
- Rejected at input where they used to pass: a chain count of zero or below, a `0` in a `CHAIN` sequence (the solvent symbol, which built a bead that occupied a site but interacted with nothing), `nan` or `inf` for any numeric keyword, an empty value for any path keyword (`RESTART_FILE :` silently ran a fresh simulation), a `RESIZED_EQUILIBRATION` axis below 7, a negative `EQUILIBRATION_OFFSET`, `QUENCH_FREQ` of zero, a non-positive `LATTICE_TO_ANGSTROMS` or `TSMMC_FIXED_OFFSET`, a `TSMMC_JUMP_TEMP` not above the target, a freeze-file directive with no IDs or an unrecognised one, and pair or angle energies that would overflow the kernels' 32-bit storage (temperature-normalised penalties are checked after scaling and rounding). `ANA_RESIDUE_PAIRS` is validated against the chains a restart run actually has. `ANALYSIS_MODULE` without `ANA_CUSTOM` is an error rather than a module that silently never runs, and `ANA_CUSTOM` without a module warns.
- `write_keyfile` output round-trips: lists were written as Python reprs, loaded objects verbatim, a `FREEZE_FILE` was dropped so the written file ran fully mobile, `QUENCH_AS_EQUILIBRATION : False` was omitted and failed the required-keyword check, and a disabled frequency was written back as an enabled analysis at the `N_STEPS + 10` sentinel cadence; a `RESTART_CONTINUE` keyfile now round-trips too. Disabled analyses are recorded explicitly rather than only as the sentinel cadence.
- `~` is expanded for every path keyword. Freeze files report unrecognised directives with line numbers. A completely full lattice aborts with the intended "overcrowded" message, and more beads than sites (`CHAIN` or `EXTRA_CHAIN`) is refused before placement rather than failing inside it with a "please report this bug" message. The occupancy-grid capacity check compared bead count against chain IDs and failed to count `EXTRA_CHAIN`. Runs in which every chain is frozen, or in which every enabled move needs longer chains than the system has, are refused at start-up instead of completing with output of a configuration that never changed (a system-wide TSMMC excursion counts only as what its sub-moves can do). `EQUILIBRATION : 0` with `RESIZED_EQUILIBRATION` switches `EQUILIBRATION_OFFSET` off along with the resize rather than failing with "RESIZED_EQUILIBRATION MUST be turned on".
- The parameter-file documentation and error message mention the five-column `A B X Y Z` super-long-range line the parser has always accepted.
- The keyfile, parameter file and freeze file are read as UTF-8 on every platform with a byte-order mark ignored, and the files that echo them are written as UTF-8 whatever the locale. A file in another encoding is refused by name with the byte offset, where it used to raise a raw `UnicodeDecodeError` (or, with a BOM, report an invisible "unsupported keyword").
- Numbers and whitespace must be plain ASCII. `1_000` and full-width or Arabic-Indic digits are refused instead of being read as some number, and a no-break space outside a comment or a file name is refused with the line and code point; it used to act as an invisible column separator.
- Refused when the keyfile is read, where they used to crash or allocate tens of GB after output had started: `CRANKSHAFT_SUBSTEPS` / `SLITHER_SUBSTEPS` / `PULL_SUBSTEPS` / `TSMMC_STEP_MULTIPLIER` (or the megamove selector they imply) above 2^31-1 or physical memory, `TSMMC_NUMBER_OF_POINTS` above 10^6, `PARALLEL_THREADS` above 1024, a box whose lattice exceeds physical memory, and `LATTICE_TO_ANGSTROMS` below 0.01. Large but possible values warn.
- Keywords that were read and silently ignored get one warning each: quench settings with no `QUENCH_RUN`, TSMMC settings with no TSMMC move, `PARALLEL_THREADS` with no `PARALLELIZE`, sub-step settings for a move never drawn, `RESTART_OVERRIDE_*` without a `RESTART_FILE`, `XTC_FREQ` / `EN_FREQ` above `N_STEPS`, repeated or self `ANA_RESIDUE_PAIRS`, and an unreachable `ANA_CLUSTER_THRESHOLD`. Their values are validated even when unused.
- An `ANGLE_PENALTY_T_NORM` whose product with the temperature overflows is a `ParameterFileException` rather than an `OverflowError`; box, resize and residue-pair errors name their keywords; `RESTART_FREQ` is announced as a number and the obsolete `CRANKSHAFT_MODE` is not announced.

#### Restart files

Restart files are validated on read (non-dictionary pickles, beads outside the box, two beads on one site, disconnected chains, non-finite energies and invalid chain IDs each raise a `RestartException` naming the offender, and a failed read leaves a previously usable object untouched) and written atomically through a temporary file, so a crash mid-checkpoint cannot destroy the previous good file. Chains are always loaded in ascending chain-ID order: a hand-built file in another order put trajectory atoms in one order and analysis columns in another, and froze the wrong beads. `add_extra_chains` no longer truncates fractional counts, and the direct TSMMC and restart APIs check their inputs for callers that bypass the parser. A hardwall restart containing a chain that crosses a periodic face is an error rather than a silent switch to periodic boundaries (not reachable through the parser).

- `RESTART_CONTINUE` protects the energy function. The checkpoint records the quench settings, which the continuation must match (a quench could be resumed with a different `QUENCH_END`, a reversed ramp or no quench at all, each a different angle-penalty scaling), and a run whose recomputed starting energy differs from the checkpoint's is refused, which also catches a changed parameter file or `ANGLES_OFF`. A continuation is refused in a directory that still holds simulation output, before anything is touched; it used to delete the stopped segment silently.
- The checkpoint is the last thing written for a step, after the step's analyses and a trajectory flush, so a run killed just after a checkpoint has lost nothing the continuation will not rewrite. Checkpoints are synced before the rename, use a per-process temporary name, and hold no numpy objects (one written under numpy 2 could not be read under numpy 1). Malformed generator states, an empty chain list and a continuation state without a temperature are refused when the file is read. The temporary checkpoint of a killed run is removed at the next start-up only when its process is known to be gone from this machine or the file is over an hour old.

#### Engine bookkeeping

- `ENERGY_CHECK` additionally cross-checks the occupancy and type grids against the chains' own positions and sequences, since a type-grid corruption made the tracked and recomputed energies wrong identically. Either kind of `ENERGY_CHECK` abort flushes a `SAVE_AT_END` trajectory and writes `CONFIG_AT_ENERGY_FAIL` before raising (the grid check used to raise before both), and the trajectory writer is always closed when a move or analysis raises.
- Energy-neutral cluster moves returned a float `0.0` and the angle energy of a chain shorter than three beads returned `0.0`, either of which turned the integer tracked energy into a float; both are integers. The hyperloop from-scratch energy oracle accumulated in 32-bit integers and wrapped silently past `2^31`.
- Lattice and chain construction and restore validate dimensions, grids, bead codes, positions and occupancy consistency before mutating anything, so an invalid backup raises cleanly rather than leaving a half-restored object. `Lattice()` itself refuses an axis shorter than 7 sites (only the parser did, and below 7 the LR and SLR shells alias), and a restore rejects occupied or typed sites that belong to no chain. The `chain_homo` fast path checks long-range-flag uniformity as well as residue uniformity. Residue-to-code assignment is deterministic across processes.
- The hardwall long-range envelope builder now uses the hardwall pair extractors, so no pair across a wall is generated in the first place (the energies were already right because the kernel dropped them). The combined short/long-range builder must keep the periodic extractors: walls are solvent, so those pairs carry the bead-solvent term.
- Latent memory-safety issues in the compiled kernels, none reachable through the engine's real call paths: a negative substep count wrapped an unsigned loop counter and read the bead selector far out of bounds, an unguarded angle-buffer write in the reference kernels, uncapped revert buffers in the serial slither and pull kernels, and a one-row over-read in lemonade's unwrap for a zero-length chain. The exported `randint` helper was wrong for any start above 1. The 2D reference kernel zeroes a coordinate on failed proposals exactly like the fast kernel.
- `RESIZED_EQUILIBRATION` carried a retry branch that extended `N_STEPS` and `EQUILIBRATION` by 100 when a chain still straddled a periodic face at the resize step, and the keyword text described it as live behaviour. It could never fire: the equilibration box is forced hardwall and a periodic restart file is refused with the keyword, so no move can leave a chain across a face there. Had it fired it would have changed the run length silently. A straddling chain at that point is a corrupted lattice state and now raises; the keyword text no longer promises the retry.
- The end-of-run "Simulation time" dropped whole days (a 50-hour run reported "2 hours"); `log.txt` mixed local time in its header with UTC in its entries.
- Every megamove kernel validates on entry what its typed signature cannot express (selector length and range, table columns, array lengths, frozen-mask length) and raises `ValueError` before touching anything; none of the failures was reachable from the engine. The parallel kernels limit the OpenMP thread count to the number of blocks.
- `Chain.positions` holds Python ints after start-up placement, rotations and pivots (they were numpy scalars, which also reached the restart file). Analysis routines are stored by name and resolved on the running `Simulation`, so a discarded one is freed without waiting for the cyclic garbage collector and a deep copy analyses itself.

#### Command line and packaging

`PIMMS --version` crashed when a stale `pimms/` directory in site-packages shadowed the package as a namespace package; the CLI now detects that and names the directory, and `--version` and `--help` no longer import the simulation stack. `PIMMS --info <typo>` and `PIMMS -k ""` exit with status 1, and `--info` lookups are case-insensitive like the keyfile. `MANIFEST.in` excludes Cython annotation HTML at every depth and generated simulation outputs left in the fixture directories, both of which shipped in earlier sdists; the distutils-era `pimms/MANIFEST` is deleted; `build.sh` also sweeps the lemonade kernel so an edited `_pbc.pyx` is recompiled, and takes the installer as its one argument, `uv` or `pip`, rather than assuming uv; it refuses to delete anything until the chosen tool is known to work. The unused `python-dateutil` dependency is dropped, the `--no-build-isolation` install instructions list `setuptools>=77` and `wheel`, the docs date a post-release build by the release it is built on rather than the unreleased top changelog entry, dead Travis and LGTM configs and an orphaned 2020 HTML readme are gone, the devtools and `pimms/data` readmes describe what is actually there, and Cython annotation HTML is ignored at any depth.

- `PIMMS -k X --info`, `-v -k X`, `-v --info` and a repeated `-k` are usage errors (exit 2) instead of silently skipping the run, dropping an option or running the last keyfile; `--keyfile` is accepted; "could not open" goes to stderr; an unwritable working directory gives a one-line error. `PARALLEL_THREADS : 0` resolves to `OMP_NUM_THREADS` if set, otherwise the CPUs the process may use, not the machine's core count.
- `mdtraj` minimum raised to 1.10.1 (1.10.0 cannot read a PDB whose atom serials have wrapped, so systems of 100,000 or more beads could not be loaded back) and `numpy` to 1.23 (1.21 could never be selected alongside mdtraj 1.10); Cython 3.0 or later is a declared build requirement. The sdist and wheel no longer carry the Cython-generated C (16 MB of a 23 MB wheel), and an install from the sdist always regenerates it. A build from a `git archive` or GitHub tarball reports its real version instead of `0+unknown`.

### Improvements and enhancements

#### Reproducibility and provenance

- **A run can now be resumed exactly.** A restart file used to be a configuration only: resuming from one started a new run, numbered from step 1, on a fresh seed, with a quench ramp restarted from the top. That remains the default and is right for staging a system or fanning out replicas, but it is not a continuation. The checkpoint now also records the step it was written at, the state of both global random-number generators at that moment and the temperature in force, and the new `RESTART_CONTINUE : True` restores all three, so the resumed segment makes exactly the moves the uninterrupted run would have made: the same `ENERGY.dat`, `RG.dat` and `QUENCH.dat` rows under the same step numbers, and the same final configuration, under periodic and hardwall boundaries, through a quench ramp, with TSMMC excursions and with `PARALLELIZE` on. `N_STEPS` is the run's total length, the resumed segment's rows carry the continued step numbers, and its trajectory's frame 0 is the checkpoint. The keyfile is checked for being the same system (no `SEED`, no `RESIZED_EQUILIBRATION` or `EXTRA_CHAIN`, the restart file's box and boundary condition, and its temperature, or in a quench a checkpoint temperature within the keyfile's `QUENCH_START` to `QUENCH_END` range, since the angle-penalty scaling is built from the keyfile), and a restart file without the state, from an earlier PIMMS, is refused with a message rather than silently resumed as a new run. Older restart files still load in the ordinary way; the four keys they carry are unchanged.
- **Every run writes the configuration it actually used.** `keyfile_used.kf` is the resolved keyword set, one line each, under a header recording the source keyfile, the PIMMS version, the date, the seed actually used, whether it was given or generated and whether it reproduces the run (it does not for a restart or a continuation), the resolved box and boundary condition, the restart file the run started from and its step, and the box and boundary condition of a resized-equilibration phase. It re-parses as a keyfile, and a run that gave no seed can be reproduced by re-running it. It exists because the keyfile a user writes is not always what ran (restart overrides, the forced hardwall of a resized equilibration, chain-type merging, seed generation), and three of the lemonade bugs fixed in this release came from post-processing having to re-derive that; lemonade's documentation now recommends passing this file. It keeps `ANALYSIS_MODULE` by path, and notes when a restart run's chain IDs are not grouped by chain type, since a re-run numbers them by its `CHAIN` lines.
- The per-step throughput in `PERFORMANCE.dat` counts the steps a resumed segment has taken, not the label of the current step.

#### Performance

- **The bookkeeping around every megamove is compiled.** Each megamove copies every bead's coordinates from the Chain objects, which hold positions as Python lists, into the kernels' integer bead table before the kernel runs, and back into lists after it returns. Written in Python, one `np.array` and one `.tolist()` per chain, that copy was not a tax on the megamove but most of it: at 12,000 beads it cost about 4 ms against 2 ms for the parallel crankshaft kernel, and the whole-chain megamoves additionally rebuilt every chain's row offset, length and homopolymer flag on every call although none of those change during a run. That was what capped `PARALLELIZE` at three to five times when the kernels alone reached eight. The two copies are now tight compiled loops over the list objects (`pimms.bookkeeping`, with the Python loops kept as the fallback and as the test oracle), the static per-chain layout is built once when the lattice is, and the bead selector no longer walks every chain to check the bead count. At 12,000 beads a parallel crankshaft megamove on four threads went from 8.1 ms to 2.3 ms, a parallel slither from 18 ms to 5.7 ms and a parallel pull from 19.5 ms to 7.1 ms; the serial crankshaft at default substeps from 5.6 ms to 2.4 ms. Nothing about the random streams changed, so every trajectory is byte-identical: the fifteen regression fixtures pass unchanged, and `pimms/tests/test_bookkeeping.py` runs whole megamoves both ways from the same seed and demands identical grids, positions and energies.
- The energy-delta kernel at the core of every crankshaft, slither and pull substep is about 35% faster: the wrapped index along each axis depends only on the offset, so 42 per-axis values are precomputed per call instead of three modulo wraps and three hardwall tests per site of the shell. Bit-exact with the reference kernels.
- **Every long-range and super-long-range energy evaluation is 2.5 to 3 times faster.** After the per-axis precomputation above, the energy-delta kernel shared by the crankshaft, slither and pull substeps still tested `hardwall` once on each of the 686 sites of its two 7x7x7 shell scans. Every caller passes that flag as a runtime value, so the C compiler kept the branch inside the innermost loop and could not unroll it; the same loop with the test hoisted runs three times faster, which no profiler could show because all of the time was simply "in the energy function". The function is now a dispatcher over a periodic body with no hardwall code and a hard-wall body, in 3D and 2D. Measured at 12,000 beads in a 60-cube: crankshaft substeps 816 to 322 ns (LR and SLR; SR is unchanged at 140 ns), heteropolymer slither 3.0x for 4-mers, 40-mers and 200-mers, pull 2.5x, the parallel crankshaft 2.7x, and hard-wall systems 1.65x. Bit-identical: every trajectory, fixture and kernel-oracle test is unchanged.
- The helpers under the slither and pull kernels (the chain-angle rescan, the bead move and revert, the pull target search and the block workers) had no `boundscheck`/`wraparound` decorators, so every memoryview access paid a range check; the directives are now module-wide. Homopolymer slither 2.9x, pull 1.1x, bit-identical.
- The compiled single-image gather allocated an occupancy grid of the whole box on every call, so a small cluster in a large box was slower than the Python fallback it replaced; it now chooses between a flat grid and a sorted-key binary search by a measured crossover, 30 to 250 times faster where the grid was the wrong choice.
- The fit report that guards the parallel slither and pull kernels cost 49 ms per megamove at 3000 chains, more than the kernel work at default substeps; it is vectorised to 2 ms. A single-block layout uses the serial kernel directly, and the parallel layout is not computed at all when `PARALLELIZE` is off.
- The four hyperloop hardwall energy branches and the hardwall pair extractor called Python-level `abs()` per pair; VMMC link probabilities use a stable `-expm1` form and cache the cutoff CDF and neighbour shells; the running-mean accumulators use the stable in-place form and avoid two temporary matrices per distance-map update; residue-pair analysis walks each chain whole once per step rather than once per pair; the empty residue-pair analysis no longer reopens its file every step.
- `MOVE_JUMP_AND_RELAX` computes the jump's energy change from the chain's local envelope, as `MOVE_CHAIN_TRANSLATE` does, instead of two whole-system energies: 30 times faster per move at 2,000 beads and 170 times at 10^4, with identical trajectories.
- The long-range cluster search rebuilt a box-sized grid for every cluster, which made the cluster analysis quadratic in the number of chains (47.7 s against 0.39 s for 4,000 dilute chains).
- A whole-system energy evaluation (start-up, `ENERGY_CHECK`, every checkpoint) folds its pair list in chunks: 12 kB per bead of transient memory becomes 3 kB in a dilute system, which was what limited the largest runnable system.
- Start-up placement no longer scans the whole lattice once per chain; chain selection and the parallel slither/pull frozen mask no longer cost a pass over every chain per step; the parallel kernels reseed one generator for the block shift instead of constructing one per megamove (119 µs against 1.9 µs); the VMMC neighbour-energy scan uses numpy for all but the shortest scans (4 to 11 times faster per call for 10-bead chains).
- Distance-map accumulators are allocated at the first `ANA_DISTMAP` sample, and the end-of-run average no longer stacks every chain's map.
- `lemonade.load()` reads only the frames selected, in bounded blocks: peak memory for a 4,001-frame, 3,000-bead trajectory fell from 1,155 MB to 164 MB.

#### Reporting

- With `PARALLELIZE` on, start-up prints and logs exactly what this box gets: the thread budget, whether the compiled kernels have OpenMP at all (a build without it is stated plainly rather than silently running serially), the crankshaft halo, block grid and movable fraction per sweep, and for slither and pull how many chains go to each kernel and the length threshold, with the split fixed for the run; a move that is not in the move set is reported as such, and the pull line counts only chains long enough to pull. The report is re-issued after a resized equilibration, after the boundary mode has switched (it used to label a periodic production box "hardwall"). `mega_crank_fast.parallel_crank_layout_info` and `openmp_info` expose the same information.
- Start-up warns when monomers are present with a per-chain move that cannot move them, with a separate sentence for cluster rotation, and when the move set cannot change any conformation (a system-wide TSMMC excursion counts as its sub-moves, not as a shape-changing move of its own). Every percolating cluster is logged. `absolute_energies_of_angles.txt` records both the requested and the applied, rounded, angle penalties.
- `REDUCED_PRINTING` now silences the per-event clash, cluster-resize, multichain-acceptance and checkpoint messages; a stray debug print of the move count is gone; `cluster_rotate` no longer emits the single-image gather's "cluster percolates" warning when it rejects a winding cluster (that warning is written for the analysis routines, where a shape computed from such a cluster is meaningless, and the move computes nothing from it, so in a condensed system it was pure noise); the quench overshoot message no longer truncates temperatures to integers; the start-up summary reports the `QUENCH_STEPSIZE` magnitude you wrote rather than the internally negated value, prints the `eq_traj.xtc` / `traj.xtc` frame split for a resized run that saves its equilibration, and its expected-frame count matches the writer's real cadence, continuations included. The run logs an explicit completion line, and the seeding messages no longer call a fixed constant the "system RAND_MAX". - The droplet surface-tension estimator skips any frame whose largest cluster spans the box, and says how many it skipped. A spanning cluster is a network or a slab, not a droplet: it has no closed interface to expand in spherical harmonics, and the single image the gather returns for it is search-order dependent, so the estimator used to fit a spectrum to noise for such frames. The usual culprit is frame 0 of a run that saved its equilibration, which is the random starting placement. Relatedly, lemonade's own spanning detector and `analyze()` no longer trigger the gather's "cluster percolates" warning for a case they measure and handle themselves; the standalone profile and cluster-shape calls still raise it, since there the warning is the only thing telling you the number is meaningless.
- lemonade warns loudly on a box mismatch, a lattice round-off residual, more than 62 chain types, a `QUENCH_RUN` temperature, and an empty frame selection (which used to fail with an `IndexError`); `Frame.polymer` is range-checked with negative indices counting from the end.
- The null-move warning counts every chain a move is too short for, not only monomers, names each move and gives the fraction of steps wasted; mobile chains too short for every enabled move are reported.
- With `PARALLELIZE`, the start-up report warns when a megamove is too small to pay for the parallel kernel's fixed cost and says what to raise the sub-step keyword to.
- Elapsed time and rates use the monotonic clock. `ENERGY.dat` and `QUENCH.dat` write integer energies exactly (same format). A warning names `ANA_DISTMAP` when the distance map of a long chain will need more than 1 GiB of memory or 256 MB of file.

#### Test suite

- **The detailed-balance tests are now statistically honest and have measured power.** The old tolerance was about thirty times the standard error and included the test trace's own spread, so a move sampling the wrong distribution inflated the tolerance it had to satisfy: an injected 50% error in the Metropolis exponent passed every case. Every fixture now uses an autocorrelation-aware tolerance built from the reference trace alone, longer traces, a guard on the test trace's integrated autocorrelation time so a fixture cannot silently become underpowered, a second observable (mean squared radius of gyration) that sees conformational bias the energy cannot, and a positive control that runs the move under test at a scaled inverse temperature and requires the assertion to fail. Mutation testing had shown four classes of bug passing the whole suite: a pivot whose rotation set never contains its own inverse, a 20% error in the Python Metropolis exponent, a wrong crankshaft proposal (invisible because the reference kernel is a transcription of the fast one, so bit-exactness cannot see a shared bug), and a 50% acceptance error in the megamove kernels. All four are now caught.
- **The 3D parallel-pull detailed-balance fixture ran single-block.** Its guard asserted that the box decomposed for the crankshaft layout, but the pull and slither kernels use the wider chain-level halo, and for that 32-cube their own layout gives one block, so the multi-block halo and interior-restricted-target logic of the 3D parallel pull had energy-consistency and thread-independence coverage but no detailed-balance test. The fixture is now a 48-cube that the pull layout splits into eight blocks, the guard asserts the pull layout and that every chain fits a block interior, and the pull's weight against the crankshaft relaxation was re-tuned so the positive control resolves again (margins 1.8 and 2.4). The 3D parallel-slither fixture decomposed, but a 40-cube leaves a 10-site block interior, so only about four of its 66 chains were eligible per sweep and they sat in two of the eight blocks; it is now a 48-cube at 2 % occupancy where roughly a fifth of 592 chains move per sweep across all eight blocks, with the same layout guard and a control margin of 2.1.
- **A physics audit of the sampling engine found nothing to fix.** An independent plain-numpy energy written from the model's definition (Chebyshev shells, empty neighbours and walls as solvent, long-range terms only between long-range beads, angle classes from the `i-1 -> i+1` displacement) agreed with the engine's tracked energy and with the from-scratch oracle, term by term, over 36 systems (2D and 3D, SR/LR/SLR, periodic and hardwall, boxes of 7, non-cubic, chains longer than the box) and after crankshaft, slither and pull megamoves through the serial, reference and parallel kernels, and through fourteen full runs with every move enabled and `ENERGY_CHECK` on. Free-draw forward and reverse transition counts against the exact Boltzmann ratio, for every move including the parallel kernels in multi-block boxes, gave no violation over several hundred transition pairs. The move-selection frequencies, the temperature in force during a quench, the system-TSMMC work sum (recomputed independently from the beta-energy trace), resized equilibration, `ENERGY_CHECK`'s detection of injected corruption, exact resumption and the kernel seeding were each checked against their definitions. The only findings were the lemonade spanning-frame averaging above, the dead resize retry, the numpy seed reduction and the droplet surface-tension accuracy note. (It could not see the two `PARALLELIZE`-only defects fixed above, the whole-box block shift and the random pass order, which need a box that does not divide evenly into blocks and a system-wide TSMMC excursion respectively.)
- New test files: proposal symmetry by free-draw forward and reverse transition counting for every Python move, plus an independent oracle for the crankshaft proposal across the fast, reference and parallel kernels (the shipped kernel is uniform over exactly the legal sites and closed under inversion in every geometry); definitional tests of `boltzmann_acceptance` against `exp(-dE/T)`; the parallel dispatch through `system_slither(parallelize=True)`; the output-file manifest, including the stale-data guarantee; move-level pins for the hardwall translation, the null-rotation accounting and the conformation-freezing warning; cluster-output pins for the long-range gather, the periodic radial profile and the percolation sentinel; lemonade pins for the effective-configuration resolution and the wetting thickness; a CLI test that runs every command-line mode from a foreign working directory with no `PYTHONPATH`; exact-Boltzmann equilibrium tests for VMMC and the crankshaft on fully enumerated state spaces; forward and reverse transition counts for single slither and pull sub-moves (the pull's Hastings ratio had no direct pin; the test rejects a 20% exponent error); `evaluate_total_energy` term by term against an independent implementation of the model definition (every energy test compared PIMMS with PIMMS); `INTSCAL` and `INTSCAL_SQUARED` against `<r>` and `<r^2>` at every gap on non-rod chains (a reintroduced `<r>^2` bug passed 150 tests); lemonade shape observables and slab and droplet surface tension against plain-numpy oracles and synthetic interfaces of known gamma (the old tests passed four injected formula errors); the kernel seeds the megamove dispatchers hand down (the old test never called a dispatcher); a guard that TSMMC excursions are actually accepted (a no-op TSMMC used to pass); and regression tests for every fix above.
- The regression harness provably tests this working tree (it used to prefer whatever `PIMMS` was on `PATH`) and pins each file's line count alongside its final line, so a cadence off-by-one is visible. The parallel tests ran on single-block boxes and now assert more than one block; the cluster moves, which had no equilibrium test at all, have crankshaft-plus-cluster tests under periodic boundaries and under a hardwall in a non-cubic box; the hardwall cluster-rotate test has a positive control; the rotation tests no longer skip straddling configurations. Tests restore the random state they change, an autouse fixture restores the working directory after every test (one test that did not made a lemonade test pass or fail with test order), and a ten-million-iteration loop no longer runs at collection time. The 2D parallel-slither detailed-balance fixture records every 8th sweep: its tolerance comes from the crankshaft reference, and a parallel sweep only moves the chains inside that sweep's block interiors, so the test trace decorrelated about eight times more slowly and a correct kernel failed about one seed in four (long runs show no bias).

It was not a bias: the 2D pull kernel's one-sub-move transition frequencies match an exactly detailed-balanced model over 803 state pairs in corners, on walls and beside other beads (566 of them with unequal forward and reverse target counts), and pull plus crankshaft reproduces the exact Boltzmann energy and wall and corner occupancy of fully enumerated 52,432- and 449,280-state systems to 0.03%. `docs/generate_keywords.py` regenerates the keyword reference from `CONFIG.py`. ## 1.0.5 (July 2026)

A round of small bug fixes and analysis-layer performance work found while auditing the codebase. Nothing here changes the physics of a simulation - the fixes are in the output files, the analysis layer, the documentation and the tooling, and the sampling itself is untouched. Every fix has a regression test; the suite grows from 640 tests to 737.

### Bug fixes: trajectory output

- **Bug fix (PDB unit cell off by one lattice site).** The `CRYST1` record in `START.pdb` was written as `(L - 1) * LATTICE_TO_ANGSTROMS`, i.e. the extent spanned by the occupied sites, rather than `L * LATTICE_TO_ANGSTROMS`, the period of the lattice (sites `L-1` and `0` are periodic neighbours one lattice unit apart). The XTC frames have always carried the correct `L * spacing` box, so the topology and the trajectory disagreed. Consequences: any PBC-aware calculation done on `START.pdb` in mdtraj/VMD was wrong by one lattice unit, and `lemonade.load(pdb=...)` without a keyfile (where the box has to be inferred from the file) inferred an `L-1` box and then wrapped the coordinates into it, silently corrupting them. For a 2D system the `c` axis is now one lattice unit, again matching the XTC.

### Bug fixes: `lemonade`

- **Bug fix ("largest cluster" meant most chains, not most beads).** `Frame.clusters` inherited its ordering from `get_cluster_distribution`, which sorts by the number of *chains* in a cluster. Everything downstream treats `clusters[0]` as the condensate — `frame.droplet`, `condensed_fraction`, `largest_cluster_size`, the radial density profile, `droplet_shape` and both surface-tension estimators. The two orderings coincide only when every chain is the same length, so in a multi-component system with unequal chain lengths lemonade was measuring the wrong cluster. Clusters are now ordered by bead count, once, in `Frame.clusters`.
- **Bug fix.** `fit_slab_profile` placed the fitted tanh centre at `length / 2`, which is only the middle of the window when the coordinate axis starts at zero. It is now anchored on `coord[0]`, so a profile the caller built on any coordinate range fits correctly. (`slab_density_profile` always starts at zero, so results from `analyze()` are unchanged.)
- `slab_density_profile` no longer accepts `min_beads`. It bins every bead in the box — which is what makes the result a density profile a coexistence fit can be run against — so the argument never did anything.

### Bug fixes: analysis and parsing

- **Bug fix.** `analysis_structures.py` raised `AnalysisStructureException` on three validation paths but never imported it, so a mismatched internal-scaling profile or distance map died with `NameError` instead of the intended, explanatory error.
- **Bug fix.** The freeze-file `B` (bead) directive split on a single space rather than on whitespace, so the empty field left by the space after the `B` made `int('')` fail: a well-formed `B` line was reported as a malformed parse error instead of reaching the not-yet-implemented guard. The bare `except:` clauses around both directive parsers are now `except ValueError:`, so they no longer swallow unrelated failures.
- **Bug fix.** `FreezeFile.validate_freeze_file`'s error message said the offending chain *was* present in the lattice — the opposite of the condition that triggers it.
- **Bug fix.** The default `RESTART_FREQ` (`"Every 10th-percentile"`) floored to `0` for runs of fewer than 10 steps, and the keyfile sanity check then rejected the keyfile with "Expected RESTART_FREQ to be larger than 0" — about a keyword the user had never set. It is now floored at 1, so short smoke-test runs work out of the box.
- **Bug fix.** `evaluate_performance` divided by a step rate of exactly zero when called on step 0.
- **Bug fix.** The "unable to find an empty lattice site" warning in `get_empty_site` printed a literal `%i` — the attempt count was never substituted in.

### Bug fixes: tooling and safety

- **Bug fix.** `pimms/test_megagrank.py` was a hand-run developer script, not a test module, but its name meant pytest imported it during collection and ran its top-level code — which called a `mega_crank.python_randint` entry point that has never existed, so a bare `pytest` at the repo root died during collection before running a single test. Renamed to `pimms/dev_megacrank_rng_check.py`, pointed at the real `randint_python` entry point, and `testpaths` is now set in `pyproject.toml` so pytest only walks the actual test packages.
- `cluster_kernels.snakesearch_single_image` indexes a flat occupancy grid by raw position with bounds checking disabled. It now validates that every input coordinate lies inside the box, turning what was silent out-of-bounds memory access into a clear `ValueError`. (The pure-Python fallback uses a dict and tolerates arbitrary coordinates, which made the divergence easy to miss.)
- **Bug fix.** Two trajectory-writing helpers in `lattice_utils` (`append_to_xtc_file_non_redundant` and `update_master_traj`, the latter on the live `SAVE_AT_END` path) caught every exception with a bare `except:` and then called `exit(1)`. That swallowed `KeyboardInterrupt`/`SystemExit`, and `exit` is the `site` builtin — absent under `python -S` — so the failure path could itself fail, and in any case it tore down the caller's process rather than letting them handle the error. Both now raise `LatticeUtilsException`. `update_master_traj` also tested `master_traj == None` rather than `is None`, which invokes mdtraj's `__eq__` instead of the identity check that is meant.

### Performance: analysis routines

Profiling a representative run (400 steps, 60 x 20-mers in a 16^3 box, `ANALYSIS_FREQ : 25`) showed **95% of the wall time going to the analysis routines** and only 0.17 s to the Monte Carlo engine itself. That run now takes **0.73 s instead of 4.89 s (6.7x)**, with the analysis block down from 4.67 s to 0.51 s (9.2x). The gain grows with chain length, because the analyses that dominated were quadratic in it: a 200-step run of 120 x 40-mers in a 24^3 box goes from **16.7 s to 1.2 s (13.7x)**.

Every change below is either bit-identical to what it replaces or, where noted, agrees far beyond the precision of the output files. Two independent checks back that up: the 15 simulation regression baselines are unchanged, and running the same simulation under the old and new code produces **byte-identical output for 29 of 31 files** - every analysis `.dat`, and bit-identical XTC coordinates. The two that differ are `log.txt` / `PERFORMANCE.dat` (timestamps and timings) and `START.pdb`, whose single differing line is the intentional `CRYST1` bug fix above.

- **`get_inter_position_distance` was 56% of the entire run** (396,000 calls). To measure the distance between two 2- or 3-element lattice positions it built two numpy arrays and dispatched `np.power` / `np.sqrt` per call, so the numpy scalar machinery cost roughly 16x the arithmetic: **6.51 us/call, now 0.42 us** in plain Python. Bit-identical (integer coordinates stay exact through the squaring; `math.sqrt` and `np.sqrt` are both the correctly-rounded IEEE-754 double root), verified over 51,000 random cases including float inputs.
- **The distance-map and internal-scaling analyses were O(L^2) Python double loops** over that function - together 2.7 s of the 4.9 s. New vectorized `lattice_analysis_utils.get_distance_matrix` and `get_internal_scaling_profile` do one numpy pass per row block / per sequence separation instead. Bit-identical. `get_distance_matrix` works in row blocks so the intermediate does not scale as `L^2 * n_dim` for long chains.
- **`get_eigenvalues_of_the_T_matrix` looped in Python over every bead**, calling `pbc_correct` and allocating an `np.outer` per bead. Now a single vectorized pass: **7.17 ms -> 0.74 ms for a 2000-bead cluster (10x)**. It also now uses `eigh` rather than the general `eig` - the gyration tensor is symmetric by construction, and `eig` can return a complex array for a matrix that is only symmetric to within rounding. Every downstream quantity is a symmetric function of the eigenvalues, so the ordering difference is immaterial; results agree to ~1e-14, against output written at 4 decimal places.
- **`ANA_POL` computed every chain's properties twice** - once minimum-image, once single-image - purely to emit a finite-size warning. For a chain that does not straddle a periodic boundary the two inputs are identical by construction and the warning cannot fire, so that case now computes once.
- **The connected-component search made over 1.4 million Python-level `get_gridvalue` calls** per analysis step, two per envelope pair. Those are now a single fancy-index into the grid per round. `get_cluster_distribution` also materialised the whole unfound-chain set (`list(...)[0]`) on every round, which made it O(n_chains^2); it uses `next(iter(...))` now, which selects the same chain.
- **Envelope-pair deduplication is a full lexicographic sort**, and once the surrounding Python loops were gone it became the single largest remaining cost. `build_envelope_pairs` / `build_all_envelope_pairs` take a new `deduplicate` argument, and the two connected-component searches - which feed the pairs straight into a set, where duplicates are harmless - pass `False`. Where deduplication *is* needed (any energy evaluation, which would otherwise double count a repeated pair) rows are now packed into a single int64 key and sorted on that, with the previous `np.void` view kept as a fallback for coordinates too large to pack.
- **`find_nearest_position`** was a Python loop over every bead; for a large condensate, choosing the snakesearch seed cost about ten times as much as the compiled BFS it feeds. Now vectorized, and `cluster_utils` hands it the position array it has already built. `np.argmin` reproduces the old strict-`<` tie-breaking exactly.
- **`Chain.get_LR_binary_array` was O(L^2) per call** (`if i in self.LR_IDX` against a list) and is called once per chain in every full energy evaluation and on every single-chain move. `LR_IDX` is fixed for the life of a chain, so the array is built once in the constructor and returned read-only.

### Performance: `lemonade`

- **`phase_separation.analyze` ran the connected-component decomposition five times per frame.** `traj[f]` mints a fresh `Frame`, so the per-Frame cluster cache was discarded between each of the five passes (condensed fraction, cluster count, largest cluster, density profile, droplet shape). Membership is now memoised on the `TrajectoryStore`: **5 decompositions per frame -> 1, and `analyze()` is 3.5x faster** (0.33 s -> 0.093 s on a 12-frame test). Only the cheap membership lists are cached - the per-cluster geometry stays on the transient `Cluster` objects so it can still be collected.
- **`_analysis.gyration_eigenvalues` materialised an `(n_frames, n_atoms, k, k)` array** before reducing it - 0.72 GB for a 1000-frame, 10k-bead trajectory and 5.8 GB at 2000 frames / 40k beads. It now accumulates the tensor one component at a time (and only the `k(k+1)/2` unique ones), holding a single `(n_frames, n_atoms)` scratch array. Bit-identical.
- **`phase_separation._shell_site_counts` listed every lattice site explicitly** as float64, so its memory scaled with box volume regardless of how many beads were being analysed. Now built from separable per-axis offsets, accumulated a slab at a time: **124 MB -> 0.5 MB on a 120^3 box**, with identical counts.

### Performance: trajectory writing

- **`SAVE_AT_END : True` was O(frames^2).** Each saved frame was added with `master_traj.join(frame)`, and `join` returns a *new* trajectory holding a copy of everything so far, so writing n frames copied `1 + 2 + ... + n` frames' worth of coordinates. Frames are now buffered in a `TrajectoryAccumulator` and joined once when the trajectory is written. (The default incremental path was moved to a persistent XTC writer in 1.0.0 for the same reason; this path had kept the quadratic behaviour.) Frame count, ordering, time stamps and unit cell are unchanged.

## 1.0.0 (July 2026)

The first stable release of PIMMS. This is a large release: the Monte Carlo engine is rewritten around fast compiled kernels and a multi-threaded sampler, several new and corrected moves are added, a new `lemonade` analysis package lands, non-cubic boxes become a first-class configuration, and the whole codebase gains a complete documentation site and an extensive correctness / detailed-balance test suite. The changes are grouped by area below.

### Compiled kernels and the fast engine

- New `pimms/mega_crank_fast.pyx`: allocation-free serial crankshaft kernels (`mega_crank` / `mega_crank_2D`) that are bit-exact drop-in replacements for the reference kernels and are wired into production. The crankshaft is the hot loop of a PIMMS run, so this speeds up essentially every simulation.
- **PRNG:** the serial kernels now draw from **splitmix64** (period 2^64, passes BigCrush, identical on every platform) instead of the platform's libc `rand()`. On macOS that was the Park–Miller MINSTD LCG — a short-period (~2.1e9), lattice-structured generator that is a poor choice for Monte Carlo. The fast and reference kernels are kept bit-identical to each other so their equivalence test still holds; the 15 simulation regression baselines were regenerated under the new generator.
- **Keyfile parser robustness:** duplicate-keyword detection for every keyword, plus typed sanity checks at startup so malformed int/float/bool values fail immediately with a clear message rather than obscurely downstream.

### Parallelization (`PARALLELIZE` / `PARALLEL_THREADS`)

- New OpenMP checkerboard kernels run the **crankshaft, slither and pull** moves multi-threaded, in both **2D and 3D**. The box is split into blocks separated by a frozen halo (width `W = R_int + 2`) so no two blocks' move footprints can touch the same site; blocks run concurrently with private splitmix64 streams and per-block integer energy deltas. The decomposition depends only on box geometry, so the result is **independent of the thread count** and targets the same Boltzmann distribution as the serial sampler.
- Whole-chain moves (slither, pull) use a chain-level decomposition: a chain parallelizes only if all of its beads fit inside one block's interior; chains spanning a boundary are frozen for that sweep.
- **Frozen chains compose with parallelization** — the parallel kernels take a per-bead frozen mask, so `FREEZE_FILE` and `PARALLELIZE` can be used together (frozen beads stay as fixed, energy-contributing obstacles but are never selected to move).
- `PARALLEL_THREADS : 0` (the default) uses all cores. Measured near-linear scaling on large dilute crankshaft/slither/pull-dominated boxes (~8× on 8 threads); little benefit for small boxes (halo-dominated) or a single concentrated droplet in a large box (load imbalance). Benchmark tables are in the docs.

### Cluster analysis performance

#### `pimms/cluster_kernels.pyx` (new compiled kernel)

- Added a Cython kernel, `snakesearch_single_image`, that reimplements the single-image ("snakesearch") reconstruction of a cluster in typed C.
	- Neighbour discovery now uses a flat occupancy-index grid (a `prod(dimensions)` array mapping each PBC position to its bead index) for O(1) lookups, replacing the Python dict of coordinate tuples and the millions of per-neighbour tuple constructions / dict lookups / per-dimension Python loops that dominated the previous BFS.
	- The seed (bead nearest the PBC-aware centre of mass) is still chosen in Python exactly as before, so the kernel is a byte-for-byte drop-in for the pure-Python routine (verified on real condensate clusters and on random self-avoiding walks, 2D/3D, both interaction thresholds).
	- Wired into `cluster_utils.convert_positions_to_single_image_snakesearch` as a fast path that transparently falls back to the pure-Python implementation if the extension has not been built.
	- End-to-end this takes cluster analysis from ~0.80 s to ~0.16 s per call on a 500-chain condensate (~5×), of which the kernel accounts for ~3×.
	- Registered as `pimms.cluster_kernels` in `setup.py`; a rebuild (`build.sh`) is required to pick it up.

#### `pimms/lattice_analysis_utils.py` — radial density profile

- Rewrote `compute_cluster_radial_density_profile` from an O(offset_max^n_dim) concentric-shell site scan to an O(num_beads) histogram: each bead's Chebyshev distance from the cluster COM is binned with a single `np.bincount`, and the density at shell k is (beads at distance k) / (lattice sites in shell k). This removes the per-site membership-test / ring-scan machinery entirely.
- **Bug fix:** the previous ring-scan loop had an off-by-one (`while offset <= offset_max` with a top-of-body increment) that emitted one extra shell at `offset_max + 1`, whose extent (2k+1 = min(box)+1) spills outside the box. Profiles are now correctly capped at `offset_max` shells. The two `*_RADIAL_DENSITY_PROFILE` regression fixtures were regenerated for the box-spanning clusters; every other row is unchanged.

#### `pimms/lattice_utils.py`

- Vectorised `center_of_mass_from_positions`: the circular (PBC-aware) mean was a per-bead Python loop calling scalar `np.cos`/`np.sin`; it is now a single vectorised computation over all beads. The integer COM output is bit-identical (checked over thousands of random cases).
- Micro-optimised `get_gridvalue`: it called `get_dimensions` (an array `.shape` lookup) on every one of its ~1M calls in the connected-component search; it now branches on `grid.ndim` and uses a single tuple index.

### Trajectory writing

- **Performance:** trajectory writing was O(frames²) — every frame reloaded and rewrote the entire XTC. Replaced the reload-append pattern with a persistent XTC writer handle (`open_xtc_writer` / `write_xtc_frame` / `close_xtc_writer`) so each frame is an O(1) append. A ~450-frame run that previously slowed to a crawl now adds ~0.6 s total.
- **New keyword `TRAJECTORY_PBC_UNWRAP`** (default `False`): when enabled, each chain is made whole across periodic boundaries before it is written, so molecules that cross a box face appear contiguous in the trajectory rather than being torn in two.
- **Bug fix (one-sided unwrap):** the single-image routine used for output shifted every boundary-crossing chain to be non-negative, which translated all such chains toward one face of the box (chains only ever appeared to bulge out of one side). Added `make_chain_whole`, which anchors the first bead in place and never applies that shift, so chains now spill symmetrically out of whichever face they actually cross.

### Non-cubic (unequal-dimension) boxes

- PIMMS now supports boxes with `x != y != z` (3D) or `x != y` (2D) under periodic boundaries as a documented, tested configuration (previously blocked behind a hardwall-off guard in the keyfile parser). An exhaustive `ENERGY_CHECK` sweep confirmed the kernels are per-axis correct for every move except cluster rotation.
- **Bug fix:** `compute_cluster_radial_density_profile` sized its shells from `max(dimensions)`, so on a non-cubic box the shells ran out to the longest axis and wrapped the short axes; it now uses `min(dimensions)` — the largest shell that fits inside every axis. Cubic boxes are unchanged.
- Cluster *rotation* is genuinely incompatible with non-cubic PBC (a cardinal 90°/270° rotation is only a symmetry of a cube), so `MOVE_CLUSTER_ROTATE` on a non-cubic periodic box now raises a clear `KeyFileException` explaining the issue rather than silently drifting the tracked energy.

### Monte Carlo moves

- **Slither (`MOVE_SLITHER`)** is now an optimized whole-system reptation megamove (2D + 3D): O(1) interaction energy for homopolymers, O(N) for heteropolymers, and single-bead chains reduce to a local translation. Detailed-balanced. `SLITHER_SUBSTEPS` sets the number of reptations applied to each chain per megamove.
- **Pull (`MOVE_PULL`, code 11)** is a new cooperative-reptation megamove for rearranging dense systems, replacing the defunct ratchet-pivot. An interior bead is displaced and the following beads are pulled along to restore connectivity (the termini are not moved), letting chains rearrange where rigid moves would clash. Detailed balance via a Metropolis–Hastings proposal-multiplicity correction; new `PULL_SUBSTEPS` keyword; requires chains of length ≥ 3.
- **VMMC (`MOVE_VMMC`, code 14)** is a new Virtual-Move Monte Carlo collective move (Whitelam & Geissler, J. Chem. Phys. 127, 154101, 2007) - hat tip to [Eric Deeds](https://deedslab.ibp.ucla.edu/) for this suggestion at BPS in 2016 (!): a seed chain is given a trial translation, neighbouring chains are recruited into a moving cluster by interaction-energy gradients, and the whole cluster translates together — escaping the kinetic traps single-chain moves hit in condensed phases. Metropolis–Hastings detailed balance with a symmetric `1/n_c` cluster-size cutoff and an exact from-scratch ΔE. New `VMMC_MAX_DISPLACEMENT` / `VMMC_MAX_CLUSTER` keywords. Remains experimental.
- **Jump-and-relax (`MOVE_JUMP_AND_RELAX`, code 13).** Previously experimental move that is now decomposed into three π-preserving sub-steps (relax → Metropolis-accepted jump → relax) whose composition is detailed-balanced. The 8 regression baselines using this move were regenerated.
- **TSMMC** temperature-excursion moves (`MOVE_CTSMMC` / `MOVE_MULTICHAIN_TSMMC` / `MOVE_SYSTEM_TSMMC`) use correct **tempered-transitions work accumulation** for detailed balance; the old `systemTSMMC` module was removed.
- The self-contained moves (slither, pull, VMMC, jump-and-relax, TSMMC) all live in `moves.py` (`MoveObject`) behind a uniform parameters-in / mutated-lattice-out interface.

### Analysis: the `lemonade` package (new)

Lemonade was previously implemented as a separate analysis package but has been brought into PIMMS in 1.0.0..
- Vectorised whole-trajectory conformational analysis — radius of gyration, centre of mass, asphericity, end-to-end distance, distance maps and internal scaling — computed for every chain in every frame in a handful of array operations, with the same quantities available as scalars at the single-chain level.
